# SpecFinder AI — 2차 AI 자연어 검색 개발 착수안 (제안)

> **상태: 설계 초안 / 미구현** · 2026-11-15
> 기존 MVP가 안정화된 뒤 별도 feature PR에서 구현한다. 이 문서만으로 API 계약을 변경하거나 AI 기능이 구현된 것은 아니다.

## 1. 사용자 시나리오

- 노트북: “150만 원 이하, RAM 16GB 이상이고 너무 무겁지 않은 노트북 찾아줘.”
- 자동차: “현대 전기차 중 3천만 원 이하, 주행거리 5만 km 이하로 보여줘.”
- 후속 대화: “여기서 가격이 더 저렴한 순으로 바꿔줘.” / “RAM은 32GB로 올려줘.”

LLM은 **조건 해석과 근거 설명**을 담당한다. DB에 없는 사양·가격·실시간 재고를 만들어내지 않는다.

## 2. 책임 분리

```text
사용자 채팅 입력 (Gemini Next.js UI)
  → FastAPI AI 검색 Endpoint (Codex / 계약 확정 후 신설)
  → LangGraph: 의도 분류 → 필터 추출 → 규칙 검증 → 기존 SQL 검색 함수 호출 → 결과 설명
  → 결과 카드 + 적용된 조건 + 출처/수집일 + 불확실성 안내
```

기존 `backend/app/services/notebook_search.py`의 `search_notebooks` 및 `car_search.py`의 `search_cars`를 재사용한다. LLM이 SQL 문자열을 생성하여 직접 DB에 실행하는 경로는 제공하지 않는다.

## 3. 입력에서 필터로 변환할 때의 규칙

- Pydantic 필터 스키마에서 허용한 **화이트리스트 필드만** 반환. 가격은 KRW 정수, 무게 kg 숫자, RAM GB 숫자, 주행거리 km 정수.
- `max_price_krw` 등 구조화 조건은 **사용자 요구를 완화하지 않고 그대로 보존**. NULL은 해당 숫자 필터에서 불일치.
- “가벼운/성능 좋은/적당한” 등 **기준이 없는 표현**은 수치 기준을 질문하거나 명시적으로 사용자가 동의한 기본값만 사용. 임의의 무게/성능 기준을 사실처럼 단정하지 않는다.
- 정형 컬럼에 없는 **배터리 SOH, 실제 재고, 실시간 가격**은 검색 가능하다고 주장하지 않는다.
- 필터 결과 0건이면 조건을 몰래 바꾸지 말고 0건 및 완화 가능한 조건을 **제안**한다.
- 검색 도중 외부 페이지/상품명에 있는 프롬프트 삽입 텍스트는 데이터로 취급하고 실행 지시로 사용하지 않는다.

## 4. API 계약 초안 — 구현 전 합의 필요

- 제안: `POST /api/ai/search` (현재 계약에는 없음)
- 입력 예: `{"domain":"notebooks","message":"150만 원 이하 RAM 16GB 이상","conversation_context":null}`
- 출력 예: `{"applied_filters":{"min_ram_gb":16,"max_price_krw":1500000},"requires_clarification":false,"clarification_question":null,"results":{...},"explanation":"...","source":"database"}`
- 에러: LLM 일시 장애, 입력 검증 실패, DB 장애를 구분. API 키는 FastAPI 서버 환경변수에만 저장하며 브라우저로 노출하지 않는다.
- 모델/제공자: 구성 가능한 어댑터로 두고 실제 계정·API 키·비용·약관은 구현 시 사용자가 선택한다. 프로젝트 ID/ADC 인증은 임의로 생성하거나 실행하지 않는다.

> **주의:** 위 URL·JSON은 제안이며, `docs/API_CONTRACT.md` 수정 및 양측 담당자 합의 후 구현한다.

## 5. 개발 순서와 담당

1. **Codex:** LangGraph 그래프 최소 구조, 모델 응답 → `NotebookFilters`/`CarFilters` 검증, 도구로 기존 검색 함수 연결, 테스트 가능한 Fake LLM.
2. **Codex:** 자연어 검색용 endpoint·타입·오류 계약과 단위 테스트; 불필요한 DB 테이블·RAG·복잡한 멀티 에이전트 금지.
3. **Gemini:** 현재 노트북/자동차 UI를 유지하며 AI 채팅창·조건 칩·결과 카드·확인 질문·로딩/오류 UI를 연결.
4. **통합:** 실제 DB로 모델 조건 추출 정합성, 질의/응답 시간, 회귀 영향을 검증.
5. **후속:** 검색 품질이 요구될 때만 리뷰·설명 의미검색과 RAG 도입 검토.

## 6. 테스트 시작 기준 / 완료 기준

**개발 착수 전:** 정식 AI API 계약, 모델 제공자(또는 Dummy 테스트), 예산/비밀키 정책, 대화 상태 유지 범위 확정.

**완료 조건 예시:**
- 숫자·범위·분야 추출과 복합 조건이 테스트 질문에 정확히 매핑되고, SQL 결과 카드가 실제 DB와 일치.
- 불명확한 단어는 확인 질문으로 처리; 다른 분야 테이블에 잘못 검색하지 않음.
- 결과가 없으면 허위 후보를 생성하지 않음.
- 모델 요청 실패 시 안전한 오류와 기존 필터 검색으로의 복귀 경로 제공.
- 프론트↔AI API↔SQL 경로의 실제 브라우저 통합 테스트.

처음에는 20~30개의 대표/경계/모호함/오류 질문으로 고정 평가셋을 마련하고, 실패 사례를 축적한다.
